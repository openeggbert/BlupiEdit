Frequently Asked Questions

Quick answers to common questions. For problems with BlupiEdit not starting or crashing, see Troubleshooting.

Can custom levels be played in the original game?

Yes — if saved to the correct slot. The original Speedy Blupi II game reads levels from the same data/ directory that BlupiEdit writes to. Save your level to a User slot (User 1–8, Design 1–20) using File → Save As, then open the game and navigate to that User collection. World slots can also be overwritten, but doing so replaces the original campaign levels.

How do I back up the original game levels?

Copy the entire data/ folder to a safe location before editing. All level files (world*.blp, user*design*.blp, info*.blp) live there. A simple folder copy is sufficient — there is no registry state or external database.

# Windows — copy data folder
xcopy "C:\Games\SpeedyBlupiII\data" "C:\Backups\SpeedyBlupiII-data" /E /I

# Linux
cp -r /games/SpeedyBlupiII/data ~/backups/SpeedyBlupiII-data

Can BlupiEdit add new item types beyond the 41 defined ones?

No — not currently. The set of item types is defined by the read-only LevelItem.ItemType enum in the source code. The .blp format stores item type as a numeric ID; the game engine interprets it. Adding a new type would require both a new enum value in BlupiEdit and support for it in the game engine, which is not modifiable in the original binary.

Why does saving overwrite unknown bytes with zeros?

BlupiEdit reconstructs the .blp file entirely from the in-memory LevelData object on save. Fields in the large unknown region (0x000A–0x0177) are not modelled — there are no corresponding C# fields to hold their values. They are written as zeros because there is nothing else to write. See BLP Format for offset details.

Does BlupiEdit work on macOS?

Untested. Mono supports WinForms on macOS but the combination has known rendering issues. The binary I/O and level parsing code is platform-independent and should work correctly. The GUI layer may have visual quirks similar to those on Linux. If you test it, please report the results in a GitHub Issue.

What is the maximum number of eggs in a level?

There is no separate egg counter — eggs are items like any other (item type 6, Egg). The total limit is 200 item slots shared across all item types in the level. A level containing only eggs could have up to 200 of them, but in practice levels also contain enemies, platforms, a goal object, and start positions, leaving fewer slots for eggs.

Can I have more than 8 user level collections?

No. The game engine and the .blp format both hard-code the limit to 8 user sets (User 1 through User 8). The level browser lists exactly these 8 slots regardless of how many info*.blp files exist. This limit is set by the original game and cannot be extended without modifying the game engine.

What does the secondary tile grid (Tiles2) do?

Unknown. The .blp format contains a second 100×100 short grid (Tiles2) at offset 0x2C79 immediately after the primary tile grid. BlupiEdit reads it and preserves it on save, but never renders or exposes it. The original game presumably uses it for a secondary layer (perhaps decoration or collision metadata), but the exact semantics have not been reverse-engineered. If you have information about Tiles2, please open a GitHub Issue.

Why does the Properties tab exist but contain nothing?

The Properties tab in the TabControl was reserved for a future level-wide property editor — a place to edit the level name, music index, background, scroll flags, and start positions. That feature was never implemented. The PropertyGrid ended up on the Objects tab instead, which works but conflates object inspection with level-wide settings. See Architecture for details.

Why are item IDs non-contiguous?

The LevelItem.ItemType enum has gaps — IDs 18, 22–23, and 35–39 are missing. These correspond to item types that were removed, repurposed, or never implemented in the version of the game that BlupiEdit targets. The original game engine likely had placeholder slots that were cut before release. The .blp format stores raw numeric IDs, so gaps in the enum simply mean those numeric values have no known behaviour.
