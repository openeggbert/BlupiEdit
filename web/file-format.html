BLP File Format

Complete binary specification of the .blp level file used by Speedy Blupi II. All offsets, sizes, and field semantics are derived directly from BlupiEdit/LevelData.cs — the authoritative source.

⚠

All multi-byte integers are little-endian. Fields marked "Unknown / reserved" are not read by BlupiEdit. When saving, BlupiEdit writes zero bytes into those positions.

Overview

A .blp level file is a flat, fixed-layout binary structure with no magic bytes, no compression, and no variable-length sections. Fields are written and read by seeking to hard-coded byte offsets. The format stores:

  • Two 16-bit version numbers
  • Level metadata (scroll mode, music index, background index)
  • Up to 4 player start positions and facing directions
  • A 40-byte level name in Windows-1252 encoding
  • Two independent 100×100 tile grids (primary and secondary layer)
  • Exactly 200 game-object records (unused slots are all-zero)

Despite sharing the .blp extension, level files and image files are unrelated formats. Image .blp files are standard Windows BMP. The file type is determined entirely by directory context.

Unknown / Reserved Gaps

BlupiEdit does not read or interpret the following regions of the file. They are present in original game level files but their semantics are unknown.

StartEnd (excl.)Bytes (decimal)Notes

⚠

Data loss on save: BlupiEdit's Save() method creates the output file from scratch with File.Create(), then seeks to known positions and writes only documented fields. The unknown regions are zero-filled in the saved file, regardless of what the original file contained. This means saving a vanilla game level with BlupiEdit may reset unknown game flags (e.g. level completion, difficulty settings, or event triggers) stored in those gaps.

ℹ

The scroll value is stored as a 32-bit integer with only the values 0 and 100 observed in practice. This may be a remnant of a "scroll speed percentage" design from the original codebase. The comparison == 100 (not != 0) means that any other non-zero value would evaluate to false.

Primary Tile Grid — Offset 0x0364

A flat array of 10,000 int16 values representing the 100×100 tile grid. Each value is an index into the Object sprite sheet (i.e. LevelData.TileImages[TileTypes.Object]). The value −1 (0xFFFF) means the cell is empty — no tile is drawn there.

OffsetSizeFieldDescription
0x036420,000 BTiles[100][100] 10,000 × int16. Iteration order: outer loop x = 0..99, inner loop y = 0..99 (x-major / column-major order). Ends at offset 0x5184. 
str.Seek(0x364, SeekOrigin.Begin);    // = decimal 868

Tiles = new short[100, 100];
for (int x = 0; x < 100; x++)
    for (int y = 0; y < 100; y++)
        Tiles[x, y] = reader.ReadInt16();
// 100 × 100 × 2 = 20,000 bytes consumed
// Stream now at 0x0364 + 0x4E20 = 0x5184 (decimal 20868)
ℹ

Iteration order is x-major (column-major): all Y values for X=0 are stored first, then all Y values for X=1, etc. This is the transposed form of what most 2-D game engines call "row-major". Keep this in mind when manually inspecting hex dumps — the first 200 bytes (100 int16s) represent the leftmost column of the level, not the top row.

Rendering — culling

The render code in MainForm.tilePanel_Paint() does not iterate all 10,000 cells — it restricts rendering to the visible viewport:

Secondary Tile Grid (Tiles2) — Offset 0x5184

Immediately following the primary tile grid is an identical-layout second tile layer. Its exact gameplay purpose is not fully reverse-engineered, but it may represent a foreground layer, a decoration overlay, or a collision-flag grid. BlupiEdit reads and preserves it faithfully on save, but does not render it.

OffsetSizeFieldDescription
0x518420,000 BTiles2[100][100] 10,000 × int16. Same x-major iteration as Tiles. Ends at offset 0x9FA4. Decimal: starts at 20868, ends at 40868.

Items Array — Offset 0x9FA4

The level contains a fixed-size array of exactly 200 item records, each 48 bytes (0x30). Unused slots (i.e. items that were never placed) are stored as 48 zero bytes — the game identifies them by Type == 0 (ItemTypes.None). BlupiEdit filters these out when loading, so only items with a non-zero type are present in the Items list.

Movement system

Items that move use a bidirectional A↔B cycle. The engine conceptually implements: 

// Pseudocode — game engine logic, not present in BlupiEdit
enum Phase { WaitA, MoveToB, WaitB, MoveToA }

Phase phase = Phase.WaitA;
int tick = 0;

void Update()
{
    switch (phase)
    {
        case Phase.WaitA:
            if (++tick >= AWait) { tick = 0; phase = Phase.MoveToB; }
            break;
        case Phase.MoveToB:
            position = Vector2.Lerp(PointA, PointB, (float)tick / ABTime);
            if (++tick > ABTime) { tick = 0; phase = Phase.WaitB; }
            break;
        case Phase.WaitB:
            if (++tick >= BWait) { tick = 0; phase = Phase.MoveToA; }
            break;
        case Phase.MoveToA:
            position = Vector2.Lerp(PointB, PointA, (float)tick / BATime);
            if (++tick > BATime) { tick = 0; phase = Phase.WaitA; }
            break;
    }
}

The ABSpeed and BASpeed properties exposed in the PropertyGrid are purely informational — they compute pixels-per-tick from the stored time and the Euclidean distance between the two points: 

ABSpeed = Math.Round(Math.Sqrt((PointB.X-PointA.X)² + (PointB.Y-PointA.Y)²) / ABTime);

Total File Size

Every .blp level file saved by BlupiEdit is exactly 50,468 bytes = 0xC524. This is a fixed size, not dependent on the number of items placed. The guarantee comes from:

  1. Known fields written at fixed offsets — gaps are zero-filled by the OS.
  2. Both tile grids always written as 10,000 × 2 = 20,000 bytes each.
  3. The item array always padded to exactly 200 records: writer.Write(new byte[0x30 * (200 − Items.Count)]).

Save Semantics — What Happens to Unknown Data

LevelData.Save(string filename) creates an entirely new file with File.Create(filename) — it does not open and patch the existing file in place. Consequence:

  • Known fields — written correctly to their documented offsets.
  • Unknown / reserved gaps — implicitly zero-filled because the OS initialises new file space to zero when the writer seeks past the current end-of-file. The gaps at 0x0004–0x00D3, 0x00DC–0x00DD, 0x00E2–0x0147, and 0x01A0–0x0363 are all zeroed on every save.
  • Original game data in gaps — permanently lost when you save. Original game levels store additional data in these gaps (the complete game state presumably). After a BlupiEdit save, those fields are all zero. 
// The save method — showing the seek / write pattern
using (FileStream fs = File.Create(filename))          // new file, all zeros initially
using (BinaryWriter writer = new BinaryWriter(fs))
{
    writer.Write(MajorVersion);                          // @ 0x0000
    writer.Write(MinorVersion);                          // @ 0x0002
    // gap 0x0004–0x00D3 left as zeros by the seek below
    writer.Seek(0xD4, SeekOrigin.Begin);
    writer.Write(HorizontalScroll ? 100 : 0);           // @ 0x00D4
    writer.Write(VerticalScroll   ? 100 : 0);           // @ 0x00D8
    writer.Seek(2, SeekOrigin.Current);                  // skip 0x00DC
    writer.Write(Music);                                  // @ 0x00DE
    writer.Write(Background);                             // @ 0x00E0
    // gap 0x00E2–0x0147 left as zeros
    fs.Seek(0x148, SeekOrigin.Begin);                    // note: fs not writer
    for (int i = 0; i < 4; i++)
    {
        writer.Write(StartPositions[i].X);               // @ 0x0148
        writer.Write(StartPositions[i].Y);
    }
    for (int i = 0; i < 4; i++)
        writer.Write(StartDirections[i] ? 1 : 0);       // @ 0x0168
    writer.WriteString(LevelName, 40);                 // @ 0x0178
    // gap 0x01A0–0x0363 left as zeros
    fs.Seek(0x364, SeekOrigin.Begin);
    for (int x = 0; x < 100; x++)
        for (int y = 0; y < 100; y++)
            writer.Write(Tiles[x, y]);                   // @ 0x0364..0x5183
    for (int x = 0; x < 100; x++)
        for (int y = 0; y < 100; y++)
            writer.Write(Tiles2[x, y]);                  // @ 0x5184..0x9FA3
    for (int i = 0; i < Items.Count; i++)
        Items[i].Write(writer);                        // @ 0x9FA4..
    if (Items.Count < 200)
        writer.Write(new byte[0x30 * (200 - Items.Count)]);
}

String Encoding — Windows-1252 (CP1252)

All strings in .blp files (level names, collection names) are encoded in Windows-1252, a single-byte code page covering Western European characters. This was the default encoding for Windows applications in the late 1990s. 

// Singleton used for all string I/O in LevelData
static readonly Encoding encoding = Encoding.GetEncoding(1252);
public static Encoding Encoding { get { return encoding; } }

// Extension: reads a null-terminated CP1252 string, always consuming <length> bytes
public static string ReadString(this BinaryReader br, int length)
{
    byte[] buffer = br.ReadBytes(length);          // always reads exactly <length> bytes
    for (int i = 0; i < length; i++)
        if (buffer[i] == 0)
            return LevelData.Encoding.GetString(buffer, 0, i);  // stop at first null
    return LevelData.Encoding.GetString(buffer);  // no null found — use whole buffer
}

// Extension: writes CP1252 string, padded / truncated to exactly <length> bytes
public static void WriteString(this BinaryWriter bw, string value, int length)
{
    if (value.Length > length)
        value = value.Substring(0, length);
    bw.Write(LevelData.Encoding.GetBytes(value));
    if (length > value.Length)
        bw.Write(new byte[length - value.Length]);   // zero-pad remainder
}
ℹ

CP1252 is a superset of ISO-8859-1 (Latin-1) for the range 0x80–0x9F, where it defines printable characters such as €, ™, ©, ä, ö, ü. ASCII characters 0x00–0x7F are identical to UTF-8. For level names consisting only of ASCII characters there is no difference.

    fs.Seek(0x872B8, SeekOrigin.Begin); ObjectTiles  = TileInfo.Read(fs);
    fs.Seek(0x88768, SeekOrigin.Begin); ElementTiles = TileInfo.Read(fs);
    fs.Seek(0x894F8, SeekOrigin.Begin); ExploTiles   = TileInfo.Read(fs);
}

// For each TileTypes group, load the BMP sheet and clone individual frames
var tmp = new List<Sprite>(BlupiTiles.Length);
using (Bitmap bmp = LoadImage("blupi000"))          // loads from IMAGE16/ or IMAGE08/
    foreach (TileInfo t in BlupiTiles)
        tmp.Add(new Sprite(bmp.Clone(t.Location, bmp.PixelFormat), t.Offset));
TileImages.Add(TileTypes.Blupi000, tmp.ToArray());   // bmp disposed; only small clones remain
// ... repeated for Blupi001–003, Object, Element, Explo

These EXE offsets are specific to the original Speedy Blupi II binary (the version shipped in the 1990s). Community patches, fan remakes, and the open-source Eggbert 2 port will have different layouts and the above offsets will not apply.
