Troubleshooting

Common problems and their solutions. If your issue is not listed here, open a GitHub Issue.

EXE Not Found / Wrong Path

Symptom: An error dialog appears on startup or after File → Open, saying the file was not found or is not a valid game executable.

Cause: The path passed to LevelData.LoadGame() does not point to a valid BLUPI.EXE.

Fix:

  • Locate your Speedy Blupi II installation directory. The executable is named exactly BLUPI.EXE (all caps on Windows; case-insensitive lookup on Linux).
  • Use File → Open and navigate manually rather than typing the path.
  • If passing the path as a command-line argument, quote paths that contain spaces: BlupiEdit.exe "C:\My Games\SpeedyBlupiII\BLUPI.EXE"

Change Level Stays Greyed Out

Symptom: The Level → Change Level menu item is always disabled.

Cause: LoadGame() must complete successfully before Change Level is enabled. If the EXE could not be loaded, the menu item stays disabled.

Fix:

  • Make sure File → Open was used and completed without an error dialog.
  • Check the title bar — it should show the path to the loaded EXE after a successful load.
  • If you passed the EXE path as a command-line argument and the menu is still greyed, the path was likely wrong. See EXE Not Found above.

Black or Missing Tiles

Symptom: The tile panel renders mostly black, or specific tile types show as blank/missing.

Cause: BlupiEdit loads sprite BMP sheets from IMAGE16/ (or IMAGE08/ as fallback) relative to BLUPI.EXE. If these directories are absent or their contents are missing, sprites cannot be loaded.

Fix:

  • Verify that the IMAGE16/ directory exists next to BLUPI.EXE and contains .bmp files.
  • On Linux, directory names are matched case-insensitively, but the directory itself must exist. If your installation has image16/ (lowercase), it will still be found.
  • If IMAGE16/ is missing entirely, BlupiEdit falls back to IMAGE08/. If both are absent, all sprites will be black.

Level Files Not Appearing in Browser

Symptom: The level browser (Level → Change Level) shows empty lists or no levels.

Cause: The data/ directory next to BLUPI.EXE is missing or empty.

Fix:

  • Confirm that data/ exists alongside BLUPI.EXE and contains .blp files.
  • On Linux, ensure the directory is named exactly data — Data or DATA will also be found via case-insensitive lookup, but the directory must exist.
  • World levels are named world<NNN>.blp; user levels are user<X>design<NNN>.blp. Both patterns must be present for their respective lists to populate.

Linux/Mono WinForms Rendering Differences

Symptom: UI elements look different from Windows — controls are misaligned, fonts are wrong, scrollbars look different.

Cause: Mono's WinForms implementation uses the platform's native GTK widgets, which renders differently from the Windows GDI+ implementation.

Known quirks under Mono:

  • Font metrics differ — text may overflow or be clipped in labels
  • PropertyGrid may have different row heights
  • Scrollbar arrows and thumb rendering use the GTK theme
  • Colour rendering in the tile panel is correct — GDI+ drawing operations behave the same

These are cosmetic issues and do not affect level loading, editing, or saving.

Saving Corrupts Unknown Bytes

Symptom: After saving and reloading a level, some data is lost or changed — specifically in the large unknown region at bytes 0x000A–0x0177.

Cause: BlupiEdit reconstructs the .blp file from scratch on save. Fields in the large unknown gap (see BLP Format) are written as zeros because their purpose is unknown. If the original file had non-zero values there, they are lost.

Workaround: Always keep a backup of the original data/ directory before editing. For World levels especially, the original values in the unknown gap may be important to the game engine.

Background Stuttering / Slow Scroll

Symptom: Scrolling the tile panel is slow or choppy, especially when a background decor image is loaded.

Cause: Background decor images (decor<NNN>.bmp) are large (640×480 px) and are loaded fresh from disk each time the tile panel repaints. There is no in-memory caching between repaints.

Workaround: This is a known architectural limitation. No fix exists in the current codebase. On fast SSDs the stutter is minimal.

Division by Zero — ABSpeed / BASpeed

Symptom: BlupiEdit throws a DivideByZeroException when displaying properties of a specific item.

Cause: The LevelItem.ABSpeed and BASpeed computed properties divide by ABTime. If ABTime == 0 (which can happen for items with coincident A/B points or default zero values), the division throws.

Fix: This is a bug in the current codebase. Until it is fixed upstream, avoid selecting items where ABTime shows as 0 in the PropertyGrid.

200-Item Limit Reached Silently

Symptom: You have more than 200 items in a level but after save and reload some items are missing.

Cause: The .blp format stores exactly 200 item slots. Items beyond slot 200 are silently dropped during save — no error or warning is shown.

Fix: Keep item counts below 200. The PropertyGrid on the level (LevelViewModel) shows the total item count — check it before saving.

Saving a User Level to a World Slot

Symptom: After File → Save As, the wrong file was overwritten — a World level file was replaced by a User level.

Cause: The Save As dialog (level browser in save mode) lets you pick any slot including World slots. If you pick a World slot while saving a modified User level, the World .blp file is overwritten.

Fix: Always verify the target slot in the Save As dialog before confirming. Keep backups of the original data/ directory. See also BLP Format → Level File Paths.
