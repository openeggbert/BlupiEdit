Architecture

Detailed reference for the code structure, class responsibilities, UI layout, and runtime data flows of BlupiEdit. All measurements and UI sizes are taken from MainForm.Designer.cs and LevelSelectForm.Designer.cs.

Architecture Overview

BlupiEdit is a single-tier Windows Forms desktop application. It does not strictly follow any design pattern, but it approximates a document-centric model: one document (the current level) is held in static state on LevelData, while the main window renders views of it. 

Presentation Layer
─────────────────────────────────────────────────────────────────
  MainForm           ─ main window, paint handlers, scrollbars, menus
  LevelSelectForm    ─ modal level browser / level slot picker
  TileList           ─ custom UserControl: scrollable tile picker

View Model Layer
─────────────────────────────────────────────────────────────────
  LevelViewModel     ─ read-only PropertyGrid adapter over LevelData

Data Layer
─────────────────────────────────────────────────────────────────
  LevelData          ─ (instance)  parsed .blp level file
  LevelData          ─ (static)    shared game state: TileImages, paths
  LevelItem          ─ one game object record from the Items array
  TileInfo           ─ one sprite frame descriptor from the EXE

  ItemTypes enum     ─ all valid LevelItem.Type values
  TileTypes enum     ─ sprite sheet identifiers
  Direction enum     ─ TileList layout direction
  LevelSelectFormMode enum

Tab 2: "Properties"

tabPage3 ("Properties") is declared in MainForm.Designer.cs but contains no controls. It is an intentional placeholder — never implemented.

Original Intent

The original design presumably intended this tab to be a level-wide property editor: a place to change the level name, music index, background decor, scroll flags, and start positions without needing an object selected. This would have mirrored the separation of concerns visible in the UI mockup — Objects tab for per-item inspection, Properties tab for level metadata.

Why It Was Never Implemented

The PropertyGrid ended up on the Objects tab instead, displaying either the selected LevelItem or the LevelViewModel wrapper (when no item is selected). This solved the immediate need — browsing level metadata — but it conflates two concerns in a single control: the grid switches context depending on what is selected.

ℹ

A future implementation could move LevelViewModel display to Tab 2 and reserve the Objects tab's PropertyGrid exclusively for item inspection. This would require only adding controls to tabPage3 — the data model (LevelViewModel) already exists.

RefreshCurrentLevelView() — the central wiring method

Called after every level load and after the tilePanel is resized. It performs the following steps in order:

  1. Early-return if LevelData.CurrentLevel == null
  2. Enable tableLayoutPanel1, tableLayoutPanel2, toolStrip1, tileList1, propertyGrid1
  3. Configure hScrollBar1 / vScrollBar1 ranges for tilePanel
  4. Configure hScrollBar2 / vScrollBar2 ranges for objectPanel
  5. Clear and repopulate tileList1.Images with TileImages[TileTypes.Object] sprites at ImageSize=64
  6. Call tileList1.ChangeSize() and reset tileList1.SelectedIndex = −1
  7. Call tilePanel.Invalidate() and objectPanel.Invalidate()
  8. Assign propertyGrid1.SelectedObject = new LevelViewModel(LevelData.CurrentLevel)

tilePanel_Paint — render pass

Step 1: Apply pixel-art render settings
  gfx.SetOptions()
  → CompositingQuality.HighSpeed, InterpolationMode.NearestNeighbor,
     PixelOffsetMode.None, SmoothingMode.None

Step 2: Draw tiled parallax background
  using (Bitmap bg = LevelData.LoadImage($"decor{level.Background:000}"))
    for (x = -scrollX/2; x < panelW + 640; x += 640)
      for (y = -scrollY/2; y < panelH + 480; y += 480)
        gfx.DrawImage(bg, x, y)
  ← background tile assumed 640×480 px
  ← background loaded fresh from disk on EVERY repaint (not cached)
  ← scroll at half speed = parallax depth illusion

Step 3: Draw visible portion of tile grid (culled)
  xStart = max(scrollX / 64, 0)
  xEnd   = min((scrollX + panelW) / 64 + 1, 100)
  yStart = max(scrollY / 64, 0)
  yEnd   = min((scrollY + panelH) / 64 + 1, 100)
  foreach visible (tx, ty):
    idx = Tiles[tx, ty]
    if (idx < 0 || idx >= sprites.Length) continue
    DrawSprite(sprites[idx], (tx*64 - scrollX, ty*64 - scrollY))

Step 4: Draw Blupi's start position
  sprIdx = StartDirections[0] ? 0 : 1   // 0 = right, 1 = left
  DrawSprite(TileImages[Blupi000][sprIdx], StartPositions[0] - scroll)

Step 5: Draw all LevelItem sprites
  foreach (item in Items):
    sprites = TileImages[item.ArtFile]
    if (item.Tile >= sprites.Length) continue
    DrawSprite(sprites[item.Tile], item.PointA - scroll)

Render Quality Settings — Why These Values

SetOptions() (defined in Extensions.cs) applies four GDI+ quality settings to the Graphics object before any drawing. Each setting is deliberately chosen for pixel-art correctness and maximum throughput:

SettingValueReason
InterpolationMode NearestNeighbor Pixels scale 1:1 with no blending. Any other mode (Bilinear, Bicubic) would blur pixel-art edges, destroying the retro aesthetic.
SmoothingMode None Anti-aliasing applies only to vector paths. Since BlupiEdit draws only bitmaps, this has no visual effect — it is set to None to suppress any overhead.
PixelOffsetMode None Keeps drawn pixels aligned to integer screen coordinates. Offset modes shift all rendering by half a pixel, which causes visible misalignment on a 1:1 pixel grid.
CompositingQuality HighSpeed Skips gamma-corrected alpha blending. Sprites use a chroma-key mask, not alpha transparency, so compositing quality has no visible impact — speed wins.

objectPanel_MouseClick — hit test

clickWorld = (e.X + scrollX, e.Y + scrollY)   // screen → world coordinates

best = null; bestDist = int.MaxValue
foreach (item in Items):
  dx = item.PointA.X - clickWorld.X
  dy = item.PointA.Y - clickWorld.Y
  dist = dx*dx + dy*dy                          // squared Euclidean distance
  if dist < bestDist AND dist < GridSize*GridSize (= 4096):
    best = item; bestDist = dist               // threshold = 64² = 4096 px²

selectedItem = best
propertyGrid1.SelectedObject = best ?? (object) new LevelViewModel(CurrentLevel)

Memory Model

All sprite bitmaps are loaded once during LoadGame() and remain in memory until the application exits. The memory footprint depends on the number and size of sprite frames:

Each Sprite struct holds a reference to a Bitmap object that was created with bmp.Clone(rect, pixelFormat). The full source BMP sheet is disposed immediately after cloning (the using block), so only the individual crop bitmaps remain in the managed heap.

⚠

The background decor image (decor{N}.blp) is not cached. It is loaded from disk on every single repaint of both panels. On spinning disks this can cause visible stutter when scrolling. A future optimisation would cache the current background bitmap and reload it only when Background changes.

Case-Insensitive Path Resolution

Windows filesystems are case-insensitive by default, but Linux (ext4, etc.) is case-sensitive. The original game files use uppercase names on Windows (e.g. IMAGE16, BLUPI.EXE). BlupiEdit's FindPathCaseInsensitive(path) handles this transparently: 

public static string FindPathCaseInsensitive(string path)
{
    if (string.IsNullOrEmpty(path)) return path;
    if (File.Exists(path) || Directory.Exists(path)) return path;  // exact match

    string parent = Path.GetDirectoryName(path);
    string name   = Path.GetFileName(path);
    if (string.IsNullOrEmpty(parent) || string.IsNullOrEmpty(name)) return path;

    string resolvedParent = FindPathCaseInsensitive(parent);  // recurse!
    if (!Directory.Exists(resolvedParent)) return path;

    foreach (string entry in Directory.GetFileSystemEntries(resolvedParent))
        if (string.Compare(Path.GetFileName(entry), name,
                           StringComparison.OrdinalIgnoreCase) == 0)
            return entry;           // first case-insensitive match wins

    return path;                    // not found — return original (will fail later)
}

The recursion resolves from the root down, so paths like /home/user/games/SPEEDYBLUPI2/data/World001.blp are correctly resolved even when all path components differ in case.

Drag-and-Drop (Unimplemented)

The TileList control fires an ItemDrag event when the user begins dragging a tile. This event is not wired to any handler in MainForm — the drag source exists but the drop target does not.

The intended workflow would have been:

  1. User selects a tile in TileList (right panel of the Tiles tab)
  2. User drags the tile onto tilePanel (left panel)
  3. On drop, the tile at the target grid cell is updated to the dragged tile index
  4. tilePanel repaints the updated cell

In addition, the MenuStrip toolbar contains two ToolStripButton items — Draw and Select — that are visible in the UI but have no Click event handlers. These were presumably placeholders for switching between a "paint tiles" mode and a "select/move tiles" mode, neither of which was implemented.

⚠

Implementing drag-and-drop tile painting is the most impactful missing feature. It would require: (1) wiring TileList.ItemDrag, (2) registering tilePanel as a drop target via AllowDrop = true and a DragDrop handler, (3) updating LevelData.Tiles[x, y], and (4) invalidating the painted cell.

How it is loaded

The file-based constructor LevelData(string filename) first attempts to open the file on disk. If the file does not exist it falls back to the embedded resource: 

// Simplified — actual code in LevelData.cs
Stream stream;
if (File.Exists(filename))
{
    stream = File.OpenRead(filename);
}
else
{
    stream = Assembly.GetExecutingAssembly()
                     .GetManifestResourceStream("BlupiEdit.Resources.DefaultLevel.blp");
}
using (var reader = new BinaryReader(stream))
{
    // parse fields at fixed offsets …
}

Because the fallback is always available (it is embedded in the EXE), the constructor never throws a FileNotFoundException. Both the default constructor and the file-based constructor always produce a fully valid LevelData instance — there is no two-phase initialisation.
